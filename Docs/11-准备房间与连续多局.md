# 11　准备房间与连续多局

[上一阶段](10-英雄跟随相机.md) · [返回实现大纲](手动实现大纲.md) · [下一阶段](12-确定性单位碰撞.md)

适用：Unity 6000.3.23f1 / UnityMOBA_Manual。以下是后续手动实施步骤，本次仅写教程文档。

## 本阶段要得到什么

服务器进程只启动一次。双方进入房间后准备，开局、结算、回房，再准备开始下一局；一人离开后当局中止，剩余玩家等待补位。每局资源与记录相互独立。

前置条件：单局联机与回放可靠。此阶段跨会话、协议、Bootstrap、HUD和记录器，先画状态机，再逐层修改。

## 1. 把进程生命周期与单局生命周期分开

| 长期对象 | 单局对象 |
| --- | --- |
| UDP监听器、连接Peer、房间成员 | CombatWorld、输入窗口、ACK历史 |
| serverInstanceId、下一个局号 | ServerMatchSession/ClientMatchSession |
| 房间Revision/ReadyEpoch | ServerAiSystem、视图单位、PlayableGraph |
| 进程记录目录 | 本局Recorder与回放流 |

监听器不得放进MatchRuntime.Dispose。世界与输入缓存不得放在长期Peer里复用。先用下图检查所有权：

```text
DemoBootstrap
  SessionServer / SessionClient     长期连接
    RoomState                      房间
    MatchSession                   每局new
  MatchRuntime                     每局new/dispose
    AI（仅服务端）
    Recorder
    客户端视图绑定与清理回调
```

## 2. 创建 RoomState

在Networking建立以下**完整数据文件** `RoomState.cs`：

```csharp
using Moba.Core;
namespace Moba.Networking
{
    public enum RoomPhase : byte
    {
        Lobby, Preparing, Countdown, Battle, Settling, Recovering, Unavailable
    }
    public sealed class MatchSummary
    {
        public ulong Number;
        public int Frame;
        public MatchResult Result;
        public bool Verified;
        public string Reason = "";
    }
    public sealed class RoomState
    {
        public ulong Revision, ReadyEpoch, MatchNumber;
        public RoomPhase Phase;
        public bool[] Occupied = new bool[2], Ready = new bool[2];
        public string Reason = "WaitingForPlayers";
        public MatchSummary LastMatch;
    }
}
```

Revision是快照新旧顺序，ReadyEpoch防止旧准备请求生效，MatchNumber隔离不同局。它们不能拿战斗Frame代替，因为每局Frame会回到0。

## 3. 建立房间状态转换表

| 当前阶段 | 触发条件 | 下一阶段与动作 |
| --- | --- | --- |
| Lobby | 双方占位且当前轮次均准备 | Preparing；创建全新单局 |
| Preparing | 两端初态校验通过 | Countdown；3秒 |
| Countdown | 到期且成员仍有效 | Battle；Start与编帧 |
| Battle | 胜负/离开/失败 | Settling；停止新帧，写结果 |
| Settling | 结算确认完成或超时处理完 | Recovering；请求清理 |
| Recovering | 资源确实释放且存储可用 | Lobby；清准备，发布快照 |
| Recovering | 释放超时/记录设施故障 | Unavailable |
| Unavailable | 后续检查资源与存储恢复 | Lobby；必须重新准备 |

离开并不是自动把新玩家接进旧战斗。补位只能进入新的准备流程。

## 4. 给每条战斗消息增加局号

按 [RoomWire.cs](../../UnityMOBA/Assets/Moba/Runtime/Networking/RoomWire.cs) 编写IsBattle、IsClientBattle、Tag、ValidateBody、Snapshot、ReadSnapshot。

Tag的格式是`ulong MatchNumber + 原payload`。包括Prepare、InitialStateAck、Countdown、Start、Input、FrameBundle、FrameAck、DesyncReport、SyncStatus、AiTrace、MatchEnd、MatchEndAck；Ping/Pong不属于单局。

处理顺序：

1. 先验证消息方向。
2. 读取非零MatchNumber。
3. 当前局：正常状态检查和处理。
4. 旧局：完整验证body格式后忽略其业务效果。
5. 未来局或非法局号：协议错误。
6. Prepare只能创建比已见最高局号更大的局，不能重复构造旧局。

同时升级LiveProtocolSignature，例如manual-room-1。阶段08无局号客户端必须被明确拒绝，不能勉强兼容。

## 5. 实现准备请求和房间快照

客户端点击准备发送`SetReady(readyEpoch, bool)`；服务端只修改该Peer所属slot。

服务端ResetReady的**方法片段**：

```csharp
Room.ReadyEpoch++;
System.Array.Clear(Room.Ready, 0, Room.Ready.Length);
```

成员加入、离开、返回房间或存储恢复时都调用。已过期请求忽略，未来Epoch拒绝；连续点击可限速，参考实现每秒最多10次处理。

PublishRoom每次增加Revision，填occupied与ready，广播完整快照。客户端仅接受更新的Revision，并以服务器快照显示状态；按钮按下可以显示“等待确认”，不能直接把本地UI状态当全员共识。

## 6. 拆出 MatchSession，并清空所有跨局状态

把阶段08SessionServer里的World、Inputs、Scheduler、History、Acks、MissingSince、Failure移动到新建ServerMatchSession；客户端对应状态进入ClientMatchSession。

每局new一次。特别检查：

- LastSubmitted从0开始，不能延续上一局帧号。
- lastTraceFrame恢复初值，不丢弃新局低帧号AI快照。
- desynced、finished、finalizingSince、delayed输入全部重置。
- FrameProduced/FrameApplied事件只注册一次；按局回调卸载后再注册。
- 不复用上一局World，即使玩家身份相同。

对照：[ServerMatchSession](../../UnityMOBA/Assets/Moba/Runtime/Networking/ServerMatchSession.cs)、[ClientMatchSession](../../UnityMOBA/Assets/Moba/Runtime/Networking/ClientMatchSession.cs)。

## 7. 结算先可靠送达，再回收

修改Finish流程：

1. 锁定当局结束，后续帧和AI评估不再执行。
2. 尝试完成记录；记录失败将verified/result报告中的记录状态处理清楚。
3. 给已进入该局的客户端发送带局号MatchEnd。
4. 客户端完成本地写入后发送MatchEndAck，载荷表示保存是否成功。
5. 服务器等确认或结算时限，处理故障Peer。
6. 触发ReleaseRequested，进入Recovering。
7. 确認资源释放后发布新的Lobby快照，清全员准备。

不能只在收到最后一帧后Dispose连接。连接应保留，单局对象才销毁。

## 8. 处理 Unity 延迟销毁

MatchRuntime.Dispose调用AI.Dispose和视图清理后，Destroy还要到帧末才真正移除。Bootstrap保存releaseFrame，ResourcesReleased委托检查：

```text
runtime == null
且当前渲染帧 > releaseFrame
且BehaviorManager.instance == null（服务端）
且本局视图/动画图计数归零（相关阶段完成后）
```

不要在纯C#SessionServer中直接读取Time.frameCount或搜索Unity对象；由Bootstrap回报检查结果。

恢复阶段不要创建下一局AI，否则会触发“已有BehaviorManager”异常。失败时进入Unavailable并说明ResourceReleaseTimeout，不能在不确定资源已清理时继续开局。

## 9. 独立目录与存储故障

目录用`<serverInstanceId>-<MatchNumber六位数>`区分同进程多局。服务端和客户端报告文件分别命名，不覆盖上一局。

开始准备前ProbeStorage：在当前记录根目录确认可创建/写入/关闭测试文件，清理自己的探测文件；不删除其他局记录。创建或结尾写入失败时进入Unavailable/记录失败处理，恢复后清准备，需要双方重新确认。

参考：[MatchRuntime](../../UnityMOBA/Assets/Moba/Runtime/Bootstrap/MatchRuntime.cs)、[RunRecorder](../../UnityMOBA/Assets/Moba/Runtime/Bootstrap/RunRecorder.cs)。

## 10. HUD与输入状态接入

房间显示服务器地址、蓝红槽位、自己、occupied、ready、上一局结果。按钮提供准备/取消、离开、上一局回放。

| 阶段 | CanControl |
| --- | --- |
| Lobby / Preparing / Countdown | false |
| Battle且世界有效 | true；缺输入等待仍可采集将来合法输入 |
| Settling / Recovering / Unavailable | false |
| 离线回放 | false |

离开、回房、打开回放时ClearPending，避免上局最后一次右键落到新局第一帧。打开上一局回放前先退出在线连接，不同时驱动在线和离线世界。

## 11. 按十轮场景验证

先两轮普通对局，确认监听器只建一次，再加入异常：

| 轮次 | 操作 |
| --- | --- |
| 1 | 用真实摧塔结束，双方回房 |
| 2 | 双方重新准备，短限帧夹具核对同步 |
| 3 | 战斗中玩家2离开；玩家1回房等待 |
| 4 | 新玩家补位，倒计时中离开 |
| 5 | 再补位并正常准备 |
| 6—10 | 继续短对局，检查资源/事件/记录增长 |

每轮记录世界帧、局号、结果、连接数、AI实例数、图形对象数和记录路径。除了第一轮，短限帧只证明生命周期，不代表十场完整自然对局。

另做旧局Input/FrameAck、旧ReadyEpoch、重复MatchEnd、未来局号、磁盘不可写测试。参考 [Run-RoomLifecycle.ps1](../../UnityMOBA/Tools/Run-RoomLifecycle.ps1)、[RoomSessionTests](../../UnityMOBA/Assets/Moba/Tests/EditMode/RoomSessionTests.cs)。

## 12. 常见问题与验收

| 现象 | 检查 |
| --- | --- |
| 第二局立刻超时 | scheduler/lastReceive/lastSubmitted是否重置 |
| 开始第二局出现两组AI | 没等Destroy完成，或事件重复注册 |
| 旧玩家准备影响新玩家 | ReadyEpoch未变化 |
| 新局输入帧仍是上一局编号 | ClientMatchSession被复用 |
| 记录看起来只有最后一局 | 目录未按局隔离 |
| 未完成写盘也回房可准备 | StorageAvailable/Settling顺序错误 |

- [ ] 同一服务器进程连续多局通过。
- [ ] 倒计时/战斗离开与补位通过。
- [ ] 旧消息不能污染新局。
- [ ] 回房资源归零，记录路径互不覆盖。
- [ ] 正常路径与Unavailable恢复均有验证记录。
