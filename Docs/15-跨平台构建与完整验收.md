# 15　跨平台构建与完整验收

[上一阶段](14-英雄死亡动画与尸体停留.md) · [返回实现大纲](手动实现大纲.md)

适用：Unity 6000.3.23f1 / UnityMOBA_Manual。本文是后续实施与验证教程；本次未进行构建、部署或运行游戏。

## 本阶段要得到什么

输出可运行的Windows客户端和Linux Dedicated Server，具备明确启动说明、测试证据、完整回放和许可证。完成标准是实际验证记录，不是仅生成exe或tar包。

前置条件：阶段00—14的验收与遗留问题已经逐项记录。本阶段先验证代码/引用，再出包，再本机与跨平台运行，最后整理交付。

## 1. 先确认构建入口和模块

打开File → Build Profiles，确认目标场景是`Assets/Moba/Scenes/MobaDemo.unity`。模板EditorBuildSettings仍可能指向SampleScene；使用下面构建脚本显式指定场景，避免打出空模板。

Unity Hub中确认当前6000.3.23f1安装了对应Linux构建和Dedicated Server模块。选择Linux Server子目标；普通Linux Player加-nographics和Dedicated Server构建是不同配置。参见 [Unity Dedicated Server构建说明](https://docs.unity3d.com/6000.3/Documentation/Manual/dedicated-server-build.html)。

不要直接把原项目Packages或ProjectSettings整目录盖过来。让当前Unity安装与Package Manager解析所需SDK/工具链，并保留依赖版本记录。

## 2. 编写资源引用检查

创建Editor/ReferenceValidator.cs，按以下顺序实现Validate方法。完整结构可对照 [ReferenceValidator](../../UnityMOBA/Assets/Moba/Editor/ReferenceValidator.cs)：

1. 场景存在，Bootstrap脚本无Missing Script。
2. Configuration可ToConfig且参数合法，Seed非零。
3. ClientPresentation中Camera、BattleView、Input、FollowCamera均绑定。
4. 四种单位Prefab及HUD存在，层级和引用完整。
5. ServerAiAgent的BlackboardAdapter、BehaviorTree、ExternalBehavior齐全。
6. 三个Profile的必需剪辑、英雄Death、Animator与武器挂点有效。
7. 动画非空，Death非循环，动画事件清空，材质为URP。
8. 输入资产能找到Moba/Point、Order、Select、Skill。
9. 运行时代码不引用UnityEditor；服务器创建路径不实例化客户端表现。

验证失败抛异常，日志写清具体资产和槽位；不要打印一句“Validate完成”却吞掉失败。

## 3. 扩展构建脚本，避免重复类方法

把阶段08的Editor/MobaBuild.cs**完整替换**成以下版本：

```csharp
using System;
using System.IO;
using UnityEditor;
using UnityEditor.Build.Reporting;

namespace Moba.Editor
{
    public static partial class MobaBuild
    {
        private const string Scene = "Assets/Moba/Scenes/MobaDemo.unity";

        [MenuItem("Moba/Build Manual Windows")]
        public static void BuildDemoWindows() => Build(
            BuildTarget.StandaloneWindows64, StandaloneBuildSubtarget.Player,
            "Builds/Demo/Windows/MobaDemo.exe");

        [MenuItem("Moba/Build Manual Linux Server")]
        public static void BuildDemoLinux() => Build(
            BuildTarget.StandaloneLinux64, StandaloneBuildSubtarget.Server,
            "Builds/Demo/Linux/MobaDemo.x86_64");

        private static void Build(BuildTarget target,
            StandaloneBuildSubtarget subtarget, string output)
        {
            if (!File.Exists(Scene)) throw new FileNotFoundException(Scene);
            // 实现ReferenceValidator后，在此调用ReferenceValidator.Validate()。
            Directory.CreateDirectory(Path.GetDirectoryName(output));
            var report = BuildPipeline.BuildPlayer(new BuildPlayerOptions
            {
                scenes = new[] { Scene },
                target = target,
                subtarget = (int)subtarget,
                locationPathName = output,
                options = BuildOptions.Development
            });
            if (report.summary.result != BuildResult.Succeeded)
                throw new Exception("Build failed: " + report.summary.result);
        }
    }
}
```

把注释中的验证调用落实后再作为正式打包入口。当前Development便于故障注入；如果后来构建非Development包，也要另跑正常路径验证并确认注入默认关闭。

subtarget用于指定Player/Server，参考 [BuildPlayerOptions.subtarget](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/BuildPlayerOptions-subtarget.html)。

## 4. 运行编译、EditMode、PlayMode

先在编辑器Test Runner运行，再建立Tools/Run-UnityValidation.ps1。可以参考原工具，但先核对Unity路径、项目根、Stage对应的方法是否已存在。

下面是人工批处理命令示例；**运行前关闭Manual的Unity编辑器**，不要让两个Unity进程同时写同一个项目：

```powershell
$unityExe = 'D:\Unity\UnityEditors\Unity 6000.3.23f1\Editor\Unity.exe'
$manualRoot = 'D:\Unity\UnityProjects\UnityMOBA_Manual'
New-Item -ItemType Directory -Path "$manualRoot\Logs\FinalValidation" -Force | Out-Null
& $unityExe -batchmode -nographics -projectPath $manualRoot -runTests -testPlatform EditMode -testResults "$manualRoot\Logs\FinalValidation\editmode.xml" -logFile "$manualRoot\Logs\FinalValidation\editmode.log"
```

PlayMode使用对应-testPlatform与不同输出路径。不要给测试命令随意加-quit，导致异步测试未完成就退出；确认Unity进程真正结束后才读取结果。需要脚本等待时使用Start-Process -WindowStyle Hidden -PassThru并等待其退出。

早期教程测试类没有统一包进Moba.Tests命名空间，因此直接照搬原脚本默认-testFilter Moba.Tests可能跑不到它们。解决方式：移除过滤器，或统一命名空间后再用过滤；无论哪种都检查实际测试数量大于0。

通过条件同时包含退出码、XML结果和Console日志；零退出码但XML不存在、0项测试或有编译异常，不能标为通过。

## 5. 本机多进程与连续房间回归

从新构建目录启动Windows服务端角色及两个客户端，使用空闲测试UDP端口，例如17777。每个进程指定独立--run-dir；如果尚未实现该参数，先在DemoBootstrap/RunRecorder增加解析再使用。

验证顺序：

1. 缺一个玩家时不能开始。
2. 双方准备后初态确认和倒计时。
3. 两端实际鼠标移动、攻击、Q、选择、跟随相机。
4. 600帧限帧测试核对逐帧hash和最终ACK。
5. 默认规则真实摧塔，记录完整结果。
6. 双方回房再准备，至少连续两局；再执行十轮混合生命周期测试。
7. 死亡尸体、复活、资源释放与回放暂停/倍速。
8. 1秒输入延迟、1秒全丢、15秒全丢、断线、单端状态偏差分别验证。

复用 [Tools工具索引](../../UnityMOBA/Tools/README.md) 中的脚本前逐个阅读。历史Lockstep/PluginSmoke工具可能依赖尚未在Manual建立的Fixture，不是把脚本放进目录就能运行。

## 6. Linux服务器实际运行

把**完整Linux构建目录**传到你有权限的新部署目录，不只传可执行文件；保留现有服务。用普通账号在可写记录目录启动，示例：

```bash
chmod +x ./MobaDemo.x86_64
run_dir="$PWD/runs/manual-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$run_dir"
./MobaDemo.x86_64 -batchmode -nographics --server --port 17777 --run-dir "$run_dir" -logFile "$run_dir/server.log"
```

这是假定你已经实现上述自定义参数的启动示例，不自动部署。不要在多个测试进程之间复用同一个run_dir。

若经公网直连，服务器操作系统防火墙与云安全组都需要允许所选UDP端口；TCP规则不等效。先确认日志已监听，再从两个Windows客户端连接。SSH登录连通不代表游戏UDP连通。

记录Linux发行版、架构、Unity版本、构建标识、配置hash、端口、两个客户端记录路径。跨系统实际三端逐帧一致才算跨平台同步通过；Linux“构建成功”只说明产物生成。

## 7. 保存可复查证据

每轮验证至少保存：

| 文件/证据 | 用途 |
| --- | --- |
| 编译与构建日志 | 版本、错误、实际目标与产物 |
| EditMode/PlayMode XML | 测试数量、失败与跳过 |
| 每进程JSON摘要与hash序列 | 核对角色、局号、结束原因、逐帧一致 |
| 完整.mobarpl与校验报告 | 脱网复现同局 |
| 弱网profile与包事件 | 证明具体注入条件 |
| 实际客户端截图/录屏 | 模型、尸体、相机与UI |
| 人工操作记录 | 真实点击与键鼠体验，不被自动测试替代 |

最终只比较lastHash不够，要比较所有相同帧号；记录缺帧也必须失败。故障演示“成功终止”与普通对局“成功获胜”采用不同预期，不把两者混成一个passed布尔。

保留三套KayKit原始许可证，插件分发遵守已有授权。不要把Library、Temp、Logs全量塞进运行包。示例回放必须来自当前规则并被当前播放器重新校验，不能复制一个不兼容旧文件装作示例。

可生成SHA-256清单记录交付文件完整性；不要把Unity .meta误当运行时依赖，也不要漏掉Player实际依赖文件。

## 10. 准备3—5分钟演示和解释

建议顺序：准备房间→移动/普攻/Q与摧塔→选机器人看节点和FSM→查看三端帧/hash→注入一次等待→回房→离线回放。

能回答以下问题，比背类名更有用：

- 为什么NoOp与缺输入不同？
- 行为树与FSM各自决定什么？
- 为什么当前位置相同却可能下一帧不同？
- UDP收到ACK为何不等于战斗已验证？
- 为什么镜头和动画可以浮点，而战斗几何用整数？
- 死亡尸体为什么不新增逻辑实体？
- 回放证明了什么，未证明什么？
- 连续多局为何要隔离ReadyEpoch、MatchNumber与Frame？
