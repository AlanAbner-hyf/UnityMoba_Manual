[上一阶段](07-消息协议与可靠UDP.md) · [返回实现大纲](手动实现大纲.md) · [下一阶段](09-回放诊断与故障处理.md)

## 本阶段要得到什么

运行 1 个独立 Windows 服务端进程和 2 个客户端，连接后完成一局帧同步对局。服务端校验并编帧，客户端不跑行为树；三个进程各自计算战斗哈希。

前置条件：阶段 07 的连接层测试通过。这里先实现单局生命周期；阶段 11 再加入玩家准备按钮和连续多局。原 SessionServer/Client 已含房间代码，按本章分层阅读，不能直接整份拷贝后忽略缺失依赖。

## 1. 固定会话公开接口

在 Networking 新建 SessionWire、ServerMatchSession、ClientMatchSession、SessionServer、SessionClient。建议保留这些公开接口以便后续 Bootstrap 不反复重写：

| 类型 | 公开职责 |
| --- | --- |
| SessionServer | 构造(port, config, seed)、Tick(now)、World、Phase、Reason、LastVerifiedFrame、Dispose |
| SessionServer 事件/回调 | MatchCreated、FrameProduced(frame,hash)、Finished、RobotInputs(frame) |
| SessionClient | 构造(connection, sampleInput, now)、Tick(now)、World、Slot、Phase、Reason、LastVerifiedFrame、Dispose |
| SessionClient 事件 | MatchCreated、FrameApplied(frame,hash)、Finished |
| 单局 session | 世界、帧缓存、输入窗口、截止时间、ACK进度；不持有长期监听器 |

SessionPhase 依次使用 Lobby、Preparing、Countdown、Running、WaitingForInput、Finalizing、Ended、Faulted。MatchCreated 必须在世界创建后、输入开始前触发，便于 Bootstrap 创建 AI 或绑定显示。

## 2. 明确每条消息的方向与载荷

在 SessionWire 里统一 WriteFrame/ReadFrame、WriteHash/ReadHash、WriteConfig/ReadConfig。哈希固定 32 字节，命令按阶段 06 的固定布局编码。

| 消息 | 方向 | 单局版载荷 |
| --- | --- | --- |
| Hello | C→S | 业务协议签名、BuildId 字符串 |
| Welcome | S→C | serverInstanceId、slot(int)、heroId(uint) |
| Prepare | S→C | BattleConfig、seed、configHash、initialHash |
| InitialStateAck | C→S | 客户端计算的 configHash、initialHash |
| Countdown | S→C | 毫秒数 3000 |
| Start | S→C | 首帧 1、输入窗口 3 |
| Input | C→S | frameId、CombatCommand |
| FrameBundle | S→C | FrameCommands、服务端执行后 hash、MatchResult |
| FrameAck | C→S | frameId、客户端执行后 hash |
| DesyncReport | C→S | frameId、expectedHash、actualHash |
| SyncStatus | S→C | serverFrame、lastVerifiedFrame、reason |
| MatchEnd | S→C | finalFrame、result、verified、reason |
| Ping / Pong | 双向 | 回显时间戳 |

本阶段不带 RoomWire 的局号前缀；阶段 11 增加并升级业务协议签名。两个中间版程序必须同时升级，不能拿原项目 demo-udp-v1 服务器来测自己的 manual-online-1 客户端。

每个 Receive 分支先检查允许的状态和方向，再读取字段，最后 RequireEnd。没有 NGO RPC 或 NetworkVariable，这些消息就是项目自己的协议。

## 3. 实现服务器接入与初态确认

先只写 Lobby→Preparing，不推进战斗：

1. SessionServer 持有一个 UdpHost(port)，每 Tick 先 TickReceive。
2. TryAccept 获取完成传输握手的连接，建立 Peer；尚未 Hello 不分配玩家槽位。
3. 收到合法 Hello 后分配空槽 0/1，并返回 Welcome。slot 对应 heroId=slot+1；满员或已开局拒绝第三人。
4. 双方已 Hello 后，构造新 ServerMatchSession、CombatWorld 和 InputWindow，触发 MatchCreated。
5. 发送 Prepare。客户端创建自己的世界、计算配置与初态哈希后发送 InitialStateAck。
6. 服务端收到两个匹配 ACK 后进入 Countdown，设置单调时间截止 now+3。未收到匹配 ACK 时不得开局。
7. Tick 超过截止后发送 Start，初始化 FrameScheduler，再进入 Running。
8. Tick 末尾始终调用 TickSend，即使业务阶段暂停或没有新战斗帧。

给 Preparing 设置 5 秒业务超时。传输握手超时和业务准备超时是两层，分别记录原因。

## 4. 实现客户端连接与未来输入

在 Bootstrap 中使用 UdpConnector。以下是**协程结构片段**，需要 DemoBootstrap 提供 clock、client、SampleInput 及错误显示方法：

```csharp
using (var connector = new UdpConnector(address, port, clock.Elapsed.TotalSeconds))
{
    while (!connector.IsCompleted)
    {
        connector.Tick(clock.Elapsed.TotalSeconds);
        yield return null;
    }
    if (connector.Error != null)
        throw new System.IO.IOException(connector.Error);
    client = new SessionClient(connector.TakeConnection(), SampleInput,
                               clock.Elapsed.TotalSeconds);
}
```

TakeConnection 将连接所有权交给 SessionClient，之后应由客户端会话每帧泵送该 peer 的 Host。不能 connector.Dispose 后把仍需使用的 Socket 一起销毁。

客户端收到 Start 时提交帧 1、2、3；之后每执行一帧，补齐未来窗口。实现 SubmitFutureInputs 的**方法逻辑片段**：

```csharp
while ((long)lastSubmitted < (long)World.State.Frame + InputWindow.Width)
{
    int frame = checked(++lastSubmitted);
    CombatCommand command = sample(frame);
    command.Validate(World.Config);
    Send(WireMessage.Create(MessageKind.Input, w =>
    {
        w.Write(frame);
        CanonicalStateWriter.WriteCommand(w, command);
    }));
}
```

sample 每次取走一次待发送输入。一次右键只放入最早尚未提交的帧，其余自动为 NoOp；不把同一个待处理点击复制进 3 帧。不要修改已经提交的帧。

## 5. 服务端只在输入完整时编帧

按下面**伪代码**实现 SessionServer.TryAdvance：

```text
n = world.Frame + 1
如果 inputs.TryTake(n) 失败：
    Phase=WaitingForInput
    记录首次 missingSince 和缺哪个 slot
    达业务时限 → Fault(InputTimeout)
    返回，不运行AI，不Step
恢复标志 = missingSince存在
清 missingSince
robots = RobotInputs(n)  // 只有这里调用服务端AI
bundle = FrameCommands(n, blue, red, robots)
world.Step(bundle)
canonical = Write(world.State); hash = SHA256(canonical)
保存 n 的 hash、canonical 和产生时间（有界历史）
触发 FrameProduced
广播相同 bundle、hash、result 给两名客户端
scheduler.Advanced(now,恢复标志)
若摧塔结束或显式测试帧上限 → Finalizing
```

原实现保留最近 128 帧证据。清理缓存时必须与 ACK 超时策略协调，不能先删尚待核对的证据再声称该帧验证通过。

## 6. 客户端执行与最终确认

收到 FrameBundle 时执行：

1. 检查已 Start，帧号必须为 World.Frame+1。
2. 调用同一 CombatWorld.Step，计算本地 hash。
3. 与包中的 hash、result 比较；一致才触发 FrameApplied，并发送 FrameAck。
4. 不一致时保存证据并发送 DesyncReport，停止执行已排队的后续战斗帧，等待服务端终止。
5. 执行成功后补齐未来输入窗口。

服务端处理 FrameAck：

- slot 取自 Peer，不取客户端自报身份。
- ACK 不能超过服务端帧，不能跳过该客户端未确认的中间帧。
- 对照该帧服务端 hash 后才更新 ACK 进度。
- LastVerifiedFrame=min(两个客户端已核对帧)。
- Finalizing 中只有双方确认到最后一帧才发 verified=true 的 MatchEnd；否则超时失败。

只打印“发出了第600帧”不代表完成600帧验证。

## 7. 心跳与错误处理

客户端可每 0.5 秒 Ping，服务器回应 Pong；所有连接管理使用同一个 Stopwatch 单调时间。

一个客户端缺输入会令另一客户端也没收到新帧，所以健康客户端不能一见停帧就立即自判断线。先显示 WaitingForServerResolution，给服务器识别缺输入方的时间；对应实现见 [SessionClient.Tick](../../UnityMOBA/Assets/Moba/Runtime/Networking/SessionClient.cs)。

坏包、版本冲突、非法方向、超窗输入和帧哈希不一致各有具体 reason。捕获可预期的协议异常并结束本局，不用空 catch 吞掉错误继续模拟。本阶段尚无 CollisionStateException，不要提前引用阶段 12 的类型。

## 8. 从本地驱动切换到正式 Bootstrap

1. 给 Bootstrap asmdef 增加 Moba.Networking、Moba.AI。
2. 将 ClientPresentation、相机、地图、光照一起保存为 ClientPresentation.prefab；HUD 独立 Prefab。
3. 场景只保留 Bootstrap；DemoBootstrap 绑定配置资产、视图 Prefab、HUD Prefab、ServerAiAgent Prefab。
4. 禁用/移除场景中的 ManualLocalBootstrap。保留其源码供离线学习，但禁止它和 SessionServer 同时 Step。
5. 参数含 --server 时：只创建 SessionServer；MatchCreated 时建 ServerAiSystem，并绑定 RobotInputs。不要创建相机、输入或HUD。
6. 普通客户端：实例化 View/HUD；连接后 Slot 决定 ControlledId；FrameApplied 更新显示。清理或结束时 CanControl=false、ClearPending。
7. Update 中给 server/client Tick 传 clock.Elapsed.TotalSeconds。OnDestroy 中释放会话、AI、连接、视图；连接协程要有取消/代次标志，防止退出后迟到连接重新绑定。

接口对照：[DemoBootstrap.cs](../../UnityMOBA/Assets/Moba/Runtime/Bootstrap/DemoBootstrap.cs)、[单局会话](../../UnityMOBA/Assets/Moba/Runtime/Networking/ServerMatchSession.cs)。

## 9. 先构建一个本机测试 Player

为了运行三个独立进程，现在就建立最小构建入口；阶段 15 再扩展 Linux 与打包。

创建 Editor 程序集 Moba.Editor，仅 Include Platforms=Editor。创建 `Editor/MobaBuild.cs`，以下为**完整起步文件**：

```csharp
using System;
using UnityEditor;
using UnityEditor.Build.Reporting;
namespace Moba.Editor
{
    public static partial class MobaBuild
    {
        [MenuItem("Moba/Build Manual Windows")]
        public static void BuildDemoWindows()
        {
            var report = BuildPipeline.BuildPlayer(new BuildPlayerOptions
            {
                scenes = new[] { "Assets/Moba/Scenes/MobaDemo.unity" },
                locationPathName = "Builds/Demo/Windows/MobaDemo.exe",
                target = BuildTarget.StandaloneWindows64,
                subtarget = (int)StandaloneBuildSubtarget.Player,
                options = BuildOptions.Development
            });
            if (report.summary.result != BuildResult.Succeeded)
                throw new Exception("Windows build failed");
        }
    }
}
```

先确认生成了完整目录，再从 Manual 项目根目录开三个终端执行（**后续人工验证命令，本次没有执行**）：

```powershell
# 终端1：同一个Windows Player以服务端角色启动
& '.\Builds\Demo\Windows\MobaDemo.exe' -batchmode -nographics --server --port 17777
```

```powershell
# 终端2和终端3各执行一次，形成两个独立客户端
& '.\Builds\Demo\Windows\MobaDemo.exe' --host 127.0.0.1 --port 17777
```

--host 是远端地址，不是 Host 玩家模式。参数解析也要在 DemoBootstrap 中实现；Unity 不会自动识别你的自定义 --server。

## 10. 验证顺序与验收

1. 只开服务器：应监听且 Frame=0。
2. 开一个客户端：仍不能推进战斗。
3. 开第二个：初态确认、倒计时、帧递增。
4. 分别右键移动：只能控制自己的英雄。
5. 双方不点击：仍提交 NoOp，战斗正常推进。
6. 运行 600 帧小测试，确认三端哈希与最终ACK；再完成真实摧塔。
7. 测错版本、第三人加入、关闭一客户端、伪造不合法输入，检查 reason。
8. 客户端日志/对象检查没有 ServerBehaviorManager，没有主动 AI Evaluate。

常见问题：只泵了接收没泵发送；忘记发送初始三帧；两端都映射成 heroId=1；Scene 里残留本地驱动；结算帧广播后立刻退出导致尾包没送达。
