# 09　回放诊断与故障处理

[上一阶段](08-独立服务端与双客户端.md) · [返回实现大纲](手动实现大纲.md) · [下一阶段](10-英雄跟随相机.md)

适用：Unity 6000.3.23f1 / UnityMOBA_Manual。本章为后续手动实施教程；命令示例尚未在模板中执行。

## 本阶段要得到什么

每局生成可离线重演的 .mobarpl；停止服务器后仍能播放、暂停、变速并逐帧验证。发生延迟、断线或状态差异时能知道卡在哪一帧、为什么结束。

前置条件：阶段 08 的一服两端可运行。先做内存流回放测试，再接文件与UI，最后注入故障。

## 1. 创建程序集和文件

Replay 程序集使用 noEngineReferences=true，引用 Moba.Core、Moba.Networking。Diagnostics 同样保持纯 C#，引用 Core。Bootstrap 引用二者。

依次创建 ReplayFormat、ReplayWriter、ReplayReader、ReplayPlayer、ReplayPlayback；Bootstrap 新增 RunRecorder；Networking 增加 FailureEvidence。不要把 UnityEngine.JsonUtility 放进纯 C# 回放模拟层。

## 2. 定义记录格式与版本

对照 [ReplayFormat.cs](../../UnityMOBA/Assets/Moba/Runtime/Replay/ReplayFormat.cs) 写固定二进制格式：

```text
文件前缀：Magic + 文件版本 + 命令编码版本
Header记录：
  规则版本、BuildId、BattleConfig、configHash、seed、initialHash
Frame记录（反复）：
  FrameCommands + 原始逐帧hash
Footer记录：
  finalFrame、result、complete、verified、reason
```

每条记录前写 int 长度，再写 byte recordKind 和内容。长度限制复用 MessageCodec.MaxBodySize，总文件默认限制 256MiB。读入前检查剩余长度，不能让损坏文件声明一个巨大数组。

规则版本、命令布局版本、文件格式版本各负责不同兼容性。阶段 12 加碰撞时改变规则与配置编码，旧无碰撞回放应拒绝，而不是强行用新规则播放。

## 3. 实现 ReplayWriter，先用 MemoryStream

按以下方法顺序写，逐方法对照 [ReplayWriter.cs](../../UnityMOBA/Assets/Moba/Runtime/Replay/ReplayWriter.cs)：

1. 构造器要求全新、可写、可寻址且长度为零的流；根据配置建立初态并写 Header。
2. Append(frame, hash) 要求 frameId=lastFrame+1，记录完整玩家与机器人命令。
3. 每 20 帧 Flush 一次；可按需求控制磁盘频率，但不能悄悄丢帧。
4. Finish 要求 finalFrame 等于最后写入帧，写 Footer 并 Flush，只允许一次。
5. Dispose 只关闭资源；没有 Finish 就留下可识别的不完整记录，禁止自动补“成功结尾”。

服务器在 FrameProduced 后记录，客户端在本地校验成功的 FrameApplied 后记录。不要录屏幕坐标，也不要每个渲染帧重复写同一条逻辑帧。

## 4. 实现 ReplayReader 的错误边界

按构造器→TryReadFrame→Footer顺序实现 [ReplayReader.cs](../../UnityMOBA/Assets/Moba/Runtime/Replay/ReplayReader.cs)：

- Header 检查 Magic、版本、规则版本、配置哈希和非零种子。
- 帧号必须连续；每条记录消费到尾，不接受重复 Header 或未知类型。
- 没读到 Footer 就到文件尾：IncompleteReplay。
- Footer finalFrame 必须等于最后记录帧，result 与标志值在合法范围。
- Footer 后还有数据：ReplayTrailingData。
- 原对局异常结束的文件不能标记 Complete=true。

用 MemoryStream 人工截断最后一个字节，测试必须失败；仅“能读到若干帧”不能判通过。

## 5. 回放只执行记录中的命令

ReplayPlayback 的核心是以下**方法逻辑片段**，world、reader、finished 等字段由类持有：

```csharp
if (reader.TryReadFrame(out var commands, out var expected))
{
    world.Step(commands);
    var actual = StateHasher.Compute(world.State);
    if (!StateHasher.Equal(expected, actual))
        throw new System.IO.InvalidDataException(
            "ReplayDesync frame=" + commands.FrameId);
}
else
{
    if (!reader.Complete || !reader.Verified)
        throw new System.IO.InvalidDataException("IncompleteReplay");
    if (world.State.Result != reader.Result)
        throw new System.IO.InvalidDataException("ReplayResultMismatch");
    finished = true;
}
```

构造时从记录的配置和种子创建 world，再比较 initialHash。离线播放绝不建立 SessionClient 或 ServerAiSystem；机器人命令已经在记录中。

完整生命周期对照 [ReplayPlayback.cs](../../UnityMOBA/Assets/Moba/Runtime/Replay/ReplayPlayback.cs)。无画面验证可以快速逐帧执行；有画面播放按20Hz和倍速调度，两个模式共用同一模拟。

## 6. 设计一次完整的回放测试

创建 ReplayTests，按这个顺序安排：

1. 使用 Match 配置创建服务器世界和内存输出流。
2. 执行固定命令序列，每一步 Step 后保存实际 hash。
3. 如果用限帧夹具，清楚标记 FixtureComplete；另写一例真实摧塔记录。
4. 写 Finish，流位置回到0，创建 Reader与第二份世界。
5. 确认没有AI实例；逐帧执行读取的命令，比较全部hash和结果。
6. 分别修改配置字段、某帧命令、某个hash、帧号，验证对应错误。
7. 删除Footer、加入尾部垃圾、改版本号，均要拒绝。

如果记录有AI，不要回放时再次调用 Evaluate。证明的是“同指令可重演”，AI 自身重新决策是否一致是另一组测试。

## 7. RunRecorder 与磁盘路径

RunRecorder 负责输出目录、流生命周期、JSON摘要、逐帧hash文件及失败报告。模拟层不承担路径选择。

建议目录：

```text
Runs/<process-id-or-unique-run>/
  process.json
  matches/<instance-id>-000001/
    server.json
    server.json.hashes
    server.json.mobarpl
```

本阶段只有一局也用单局子目录，为阶段 11 做准备。使用 CreateNew 或唯一目录，已有记录不得被下一次启动覆盖。File.OpenWrite 可能保留旧尾部，不能代替新文件创建语义。

区分 simulationVerified 与 recordingSucceeded：游戏状态一致，但磁盘写入失败，应显示记录失败，不把空回放当作成功交付。

## 8. 在 HUD 展示可解释的信息

先建立 DemoHud，使用代码绘制最小信息，不必立即做复杂Canvas。按三块摆放：

| 区域 | 字段 |
| --- | --- |
| 连接/控制 | 地址、端口、连接/退出、回放路径、打开回放 |
| 同步 | 本地Frame、ServerFrame、LastVerifiedFrame、等待/结束原因 |
| 观察 | SelectedId、HP、FSM、当前意图、AI快照BasedOnFrame/CommandFrame |

AI 观察快照超过1秒未更新显示“已过期”；它不参与战斗判定。

给HUD留独立区域，例如左侧300px；用Camera.rect或明确的屏幕Rect阻止在该区域产生Order。OnGUI坐标y向下，InputSystem屏幕坐标y向上，转换时别混用。UI焦点正在输入路径/地址时，Q不应该触发技能；可由HUD输出输入占用状态交给PlayerCommandInput。

## 9. 暂停与倍速使用独立播放时钟

打开回放前关闭在线连接和旧局资源，再 Bind回放世界。增加 Paused、Speed和累计播放时间，不修改CombatWorld中的帧长：

```text
若暂停：
    不读下一帧；不累计要补跑的播放时间
否则：
    累加 unscaledDeltaTime × speed
    每满1/20秒，Advance一次；受每渲染帧预算限制
    Advance成功后刷新视图
```

View.PresentationPaused与PlaybackSpeed也要同步；否则逻辑暂停但插值/动作还在走。阶段 13 将用同一逻辑显示时间控制骨骼动画。

UI按钮测试不能仅调用回放类方法代替：后续人工检查实际点击暂停、恢复、倍速。

## 10. 增加业务故障注入

在开发构建条件下启用，普通启动默认关闭：

| 注入 | 插入位置 | 预期 |
| --- | --- | --- |
| 指定帧输入延迟1秒 | 客户端输入编码后、传输前排队 | 服务器停在缺输入帧，补到后恢复 |
| 禁止FrameAck | 客户端执行成功后 | 服务端ACK超时，不能伪造Verified |
| 指定帧HP+1 | 一个客户端Step后、ComputeHash前 | 该帧检测差异并终止 |
| 退出客户端 | 实际关闭进程或可靠离开 | 服务器检测断线并结束 |

输入延迟不是UDP丢包；两者分别验证。状态注入需要测试受控访问，可使用Core内部测试接口或既有FaultInjector方式，不能为网络调用公开“任意改血”接口。

## 11. 增加数据报故障注入

在阶段 07 数据报端口上下行外层加入 DatagramFaultInjector。使用固定随机种子，但注明真实进程调度仍会影响报文生成时机。

参考 [weak-101](../../UnityMOBA/Tools/UdpProfiles/weak-101.json)：每方向100±30ms延迟、5%丢包、2%复制、10%额外延迟。只在一个客户端施加同一配置，避免服务器再次叠加。

先测1秒全丢，再测15秒全丢：前者应等待并恢复，后者应在超时后明确终止。记录实际参数、数据报动作、帧号、重传和结果；仅说“弱网通过”没有可复查意义。

## 12. 失败证据与验收

FailureEvidence至少保留首个差异帧、两端hash、服务端最新帧、已确认帧、配置标识、近期命令或规范化状态。首次差异一旦记录，不用后续连锁错误覆盖它。

常见问题：Dispose自动写成功Footer；实时AI参与回放；暂停后追赶累计墙钟；只比较最终hash；记录写入异常被吞掉；调试快照影响可靠业务窗口。

- [ ] 完整回放脱网逐帧通过。
- [ ] 损坏、缺Footer、版本不匹配有明确错误。
- [ ] 暂停/倍速与显示时间一致。
- [ ] 延迟、断线、状态篡改和弱网分别有日志。
- [ ] 原项目历史测试不直接标成Manual已通过。
